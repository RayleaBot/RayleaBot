# Release Notes

本目录保存 GitHub Release 的中文正文，每个完整版本标签对应一个 UTF-8 Markdown 文件，例如 `v0.4.0.md`。文件名包含 `v`，正文从版本摘要开始；发布标题由工作流设置为 `RayleaBot <tag>`。

功能版采用约一页的精编正文；补丁版通常为 150–300 个中文字，不计下载表和链接。重要升级操作与兼容性说明完整保留。

## 当前候选

[v0.4.0](./v0.4.0.md) 是本轮全新分发的候选说明，尚未公开发布。实际产物与最终平台验收完成前，不填写未经核实的下载链接，也不将候选验证标记为正式发布验收。

## 编写与发布

1. 从[发布说明模板](../release-notes-template.md)复制功能版或补丁版正文，在本目录创建与目标标签同名的文件。
2. 按目标版本的变更填写中文说明，替换所有 `{{...}}` 占位符，删除编辑注释及没有内容的可选栏目。核对升级范围、插件兼容性、平台包、更新方式和完整变更链接。
3. 在仓库根目录检查目标版本。以 `v0.4.0` 为例，先创建对应文件，再执行：

   ```text
   python scripts/release/check_release_notes.py --tag v0.4.0
   python scripts/check-doc-links.py
   ```

4. 将审阅后的正文随版本代码一起提交，目标标签必须指向包含这份文件的提交，再按发布流程推送标签。
5. [release 工作流](../../../.github/workflows/release.yml)先检查正文，再构建平台包、执行现有验证与签名步骤；发布时通过 `body_path` 读取正文，并上传发行包、发布清单、签名和校验文件。

正文检查会拒绝：不符合 release contract 版本格式的标签、同名文件缺失、非 UTF-8 内容、空白或仅含标题/分隔线/HTML 注释的正文，以及残留的 `{{...}}` 占位符。标签版本格式直接读取[发布 contract](../../../contracts/release-manifest.schema.json)。检查失败时，平台构建与发布不会执行。

检查脚本不生成正文，也不验证描述的事实或未来下载地址。发布者需要根据目标标签、实际产物和验证结果核对内容；操作步骤见[交付与升级](../delivery-and-upgrade.md)。PR 与主分支 CI 的 release-helper job 通过现有测试发现机制执行正文检查脚本的回归测试。

## 历史与修订

- 本目录维护面向用户的发布正文；[`docs/CHANGELOGS/`](../../CHANGELOGS/README.md)保留历史能力与工程归档，通过链接关联，避免同一正文重复维护。
- 以本流程发布的版本，正文文件随标签保存；既有标签不补写文件、不改写历史归档。
- 重跑同一标签的发布工作流，会重新使用该标签中的文件更新 Release 正文。直接在 GitHub 修改正文后，重跑可能覆盖该修订；需要保留发布后勘误时，应记录修订并避免把重跑构建当作文案更新入口。
- 新标签的说明文件必须提交到该标签所在提交，仅存在于本地工作区或主分支较新的提交中不能被该次发布读取。
